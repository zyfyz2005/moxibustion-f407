# 基于 STM32F407ZGT6 + FreeRTOS 的艾灸控温控时报警装置 —— 设备端重构项目计划书

> 版本 v12 · 2026-10-02
> 本版只保留要实施的内容。硬件事实以第三节为准。
> **v12 变更：删掉 24C02 配置持久化**——阈值与时长改为只在内存生效。原因是实测发现板上 24C02 的
> SCL（6 脚）与 PB8 不通、该脚电压为 0 V（SDA 一侧正常），判定为板级断线；权衡之后决定不做这个
> 只需要两个数、收益有限的功能。随之删除 ConfigTask、`config_req_queue` / `config_resp_queue`、
> token 匹配机制与 I2C1 外设。任务数 6 → 5，队列 6 → 4。
> v11 变更：按《STM32F407艾灸装置-原理图信息核对清单》逐脚复核引脚，更正 4 处、新增 1 处。

## 一、项目来源与定位

- **来源**：一个艾灸控温控时报警装置课题。原版设备端是 ESP32-C3 双板方案，上云走 easyiothings 平台；本项目是**我个人独立完成的第二版设备端实现**，改用一块 STM32F407ZGT6 从头做，与课题交付物无关。
- **本版核心变化**：单板合并（采集、控制、报警、联网全由一块普中麒麟 STM32F407ZGT6 承担），主控从"非阻塞主循环"升级到 FreeRTOS 多任务，并新增任务级看门狗。
- **保留**：DHT11 温湿度、按键 30ms 消抖、倒计时、高温阈值、报警、静音、复位、MQTT 上云与指令下发、报警节奏（响 200ms / 停 150ms）。
- **新增**：FreeRTOS 6 任务、板载 ESP8266 模组联网、IWDG 看门狗与任务心跳检查。
- **没有屏幕后怎么看设备状态**：板载 LED（PF9/PF10）编码表示状态 + 调试串口打印带时间戳的日志。运行日志只从调试串口输出，不落盘。

## 二、系统架构

```text
┌──────────────────────────────────────────────────────────────┐
│              普中麒麟 STM32F407ZGT6（单板）                  │
│                                                              │
│  DHT11 ─单总线─► SensorTask ─sensor_queue(4)─┐               │
│  按键  ─GPIO───► ControlTask ◄─cmd_queue(8)──┘               │
│                     │                                        │
│                     │   状态：g_moxa_state + state_mutex     │
│                     │   （唯一写入者：ControlTask）          │
│                     ▼                                        │
│              ack_queue(8) ◄── 唯一生产者：ControlTask        │
│                     │         （NetTask 仅 busy 兜底）       │
│                     ▼                                        │
│   AlarmTask ◄── EVT_STATE_ALARM（读共享状态）                │
│   NetTask   ◄── EVT_STATE_NET（读共享状态）+ cmd_queue 生产者│
│                     │                                        │
│              NetTask ──at_tx_queue(8)→ ESP8266 → MQTT        │
│                                                              │
│  DogTask ─每 500ms 检查心跳─► 喂 IWDG                        │
└──────────────────────────────────────────────────────────────┘
```

**ACK 路径只有一条**：ControlTask 生成 → `ack_queue` → NetTask 发布。v12 删掉 ConfigTask 之后，这条路径上再没有任何旁路；唯一例外仍是 `cmd_queue` 入队失败时由 NetTask 直接回 `code=3 busy`。

### 任务表

| 任务 | 优先级 | 栈（word） | 职责 | 资源 |
|---|---:|---:|---|---|
| DogTask | 7 | 256 | 检查各任务心跳是否在各自期限内推进，全部达标才喂 IWDG | IWDG |
| ControlTask | 5 | 512 | 按键消抖、状态机、倒计时、阈值判断、指令校验、改参数、ACK 生成、秒计数、堆占用打印 | GPIO、sensor_queue、cmd_queue、ack_queue |
| AlarmTask | 4 | 256 | 蜂鸣器节奏、LED 状态、报警事件 | PF8（TIM13_CH1）、PF9、PF10 |
| SensorTask | 3 | 256 | DHT11 采集（2s 周期）、传感器健康检查 | DHT11 IO、DWT/TIM 延时 |
| NetTask | 2 | 1024 | AT 命令状态机、WiFi 连接、MQTT 上线、遥测发布、指令订阅、ACK 发布、重连 | USART3（PB10/PB11）、PF6 模组使能、PC0 模组状态灯、at_tx_queue |
| IdleTask | 0 | — | FreeRTOS 空闲任务 | — |

栈深单位是 word（CM4 上 1 word = 4 B），合计约 10 KB。**NetTask 的 JSON / AT 缓冲一律静态分配，不放栈上**；所有任务禁止运行期动态 malloc。

### 接口定义

**共享状态**（`state_mutex` 保护，ControlTask 唯一写入者）：

```c
typedef struct {
    uint8_t  state;        // 0=WAITING  1=COUNTDOWN  2=ALARM
    uint8_t  muted;        // 静音标志，与 state 正交
    uint8_t  switch_on;
    uint8_t  temp_valid;
    int16_t  temp_c;
    uint16_t humi_pct;
    uint32_t remain_s;
    uint16_t th_max_c;
    uint32_t duration_s;
    uint8_t  temp_alarm;
    uint8_t  countdown_alarm;
    uint32_t uptime_s;     // 独立秒计数器，见下方说明
    uint16_t err_cnt;
    uint32_t seq;          // 每次变更自增，消费者据此判断有无新数据
} MoxaState_t;
```

**`uptime_s` 不来自 `HAL_GetTick()/1000`**：`HAL_GetTick()` 是 32 位毫秒，约 49.7 天回绕，除 1000 会在第 49.7 天出问题。改由 ControlTask 在 10ms 轮询里用计数器每满 1000ms 对独立的 `uint32_t uptime_s` 加一，可跑约 136 年。

**指令**（NetTask → ControlTask）：

```c
typedef struct {
    uint16_t msg_id;   // 由下行指令携带，NetTask 原样透传，设备侧不分配
    uint8_t  cmd;      // START / STOP / RESET / MUTE / QUERY / SET_TH / SET_DUR
    int32_t  value;
    uint32_t rx_tick;
} CmdMsg_t;
```

**回执**（ControlTask → NetTask）：

```c
typedef struct {
    uint16_t msg_id;
    uint8_t  cmd;
    uint8_t  code;     // 0=ok 1=unknown_cmd 2=bad_param 3=busy 4=format_err 5=config_io_err
    uint8_t  state;    // 以 ControlTask 生成时刻为准，不在发送时刷新
} AckMsg_t;
```

**`state` 取值时机**：ACK 里的 `state` 是"处理这条指令那一刻的状态"，语义是"这条 msg_id 的处理结果"。它被放进 `at_tx_queue` 后即使排队等待，也**不在发送时刷新**，否则 ACK 就变成"发送时刻的状态"，与 msg_id 对应的处理结果对不上。

**`msg_id` 的用途**：**由下行指令携带，NetTask 原样透传，设备侧不分配、不回绕、不判重**。它唯一的用途是回 ACK 时让客户端对上是哪条指令。

> **v12 说明**：原来这里还有一套"设备侧 token 匹配"（防客户端复用 `msg_id` 导致迟到响应串号）。
> 删掉配置持久化之后，改参数不再有异步回执，这套机制整块消失了；`ConfigReq_t` / `ConfigResp_t` 两个结构体也一并删除。

**AT 待发项**（NetTask 内部队列元素，不放大报文）：

```c
typedef struct {
    uint8_t  kind;     // AT_TX_TELEMETRY / AT_TX_ACK
    uint16_t msg_id;
    uint8_t  code;     // AT_TX_ACK 时使用
    uint8_t  cmd;
    uint8_t  state;    // AT_TX_ACK 时使用，取自 AckMsg_t，不在发送时刷新
} AtTxItem_t;
```

**ACK 生产者的唯一例外**：正常路径 ACK 全部由 ControlTask 生成；**唯一例外是 `cmd_queue` 入队失败时由 NetTask 直接生成 `code=3 busy`**。发布者始终只有 NetTask。

### 队列与满策略

| 队列 | 深度 | 生产者 → 消费者 | 满了怎么办 |
|---|---:|---|---|
| `sensor_queue` | 4 | SensorTask → ControlTask | 丢最旧再入队 |
| `cmd_queue` | 8 | NetTask → ControlTask | NetTask 用 0 超时；失败直接回 busy ACK，`err_cnt++` |
| `ack_queue` | 8 | ControlTask → NetTask | ControlTask 用 0 超时；失败先丢队头最旧的一条 ACK 腾出一格，**随后必然能入队**（单生产者单线程，不存在再被抢占的情形），不重复重试。**绝不阻塞** |
| `at_tx_queue` | 8 | NetTask 自身（遥测周期 + ack_queue 取出的 ACK） | 优先丢最旧的一条 TELEMETRY；若队里没有遥测项，则丢弃新条目并 `err_cnt++` |

所有队列只传上面的固定结构体，**不传 JSON 字符串**。

### 改参数路径（同步，只改内存）

1. NetTask 解析下行指令，`msg_id` 原样透传 → 发 `cmd_queue`。指令缺失 `msg_id` 或 `msg_id == 0` → 直接回 `code=4 format_err`，不入队。
2. ControlTask 判定顺序**先 cmd 后 value**：
   - `cmd` 不在支持列表 → `code=1 unknown_cmd`，结束。
   - `cmd` 已知但不是配置类（如 `query` / `mute`）→ 直接执行并生成对应 ACK。
   - `cmd` 是配置类（`set_threshold` / `set_duration`）→ 再判 `value`：阈值 20–60 ℃、时长 1–3600 s，越界 → `code=2 bad_param`，结束。
3. 合法 → **直接改内存里的运行参数、立即生效**，回 `code=0`。

**v12 说明**：这条路径以前是"异步写 24C02 + token 匹配"，现在简化成了一步内存赋值。
随之消失的：`config_req_queue` / `config_resp_queue` 两套队列、设备侧 token、300 ms 超时回执，
以及 `code=3`（配置在途）与 `code=5`（配置读写失败）这两条错误路径——**协议里保留编号，但当前实现不会产生**。
代价是**断电后参数回到默认值**（阈值 40 ℃、时长 60 s）。
启动时也不再需要"在调度器之前读 I2C"那段硬约束，配置直接取 `app_cfg.h` 的默认值。

### 事件位分配

```c
#define EVT_STATE_ALARM   (1u << 0)   // 只有 AlarmTask 等这一位
#define EVT_STATE_NET     (1u << 1)   // 只有 NetTask 等这一位
#define EVT_ALL_STATE     (EVT_STATE_ALARM | EVT_STATE_NET)
```

生产者 `xEventGroupSetBits(eg, EVT_ALL_STATE)`；消费者 `xEventGroupWaitBits(eg, MY_BIT, pdTRUE, pdFALSE, timeout)`——`pdTRUE` 只清自己那一位。醒来后加 `state_mutex` 拷贝状态，用 `seq` 判断是否真变过，再释放锁。

### FreeRTOS 配置

| 配置项 | 取值 |
|---|---|
| API 风格 | **原生 FreeRTOS API**（`xTaskCreate` / `xQueueSend` / `xEventGroupWaitBits`），不使用 CMSIS-RTOS v2 包装 |
| `configTICK_RATE_HZ` | 1000 |
| `configMAX_PRIORITIES` | 8 |
| 堆方案 | heap_4，`configTOTAL_HEAP_SIZE = 32 KB` |
| `configCHECK_FOR_STACK_OVERFLOW` | 2 + `vApplicationStackOverflowHook` |
| 启用项 | mutex、event_groups、task_notifications |
| `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` | 5 |

选原生 API 的理由：本文所有接口定义（事件组专属位、任务通知、队列 clear-on-exit 语义）在原生 API 下才是字面对应的；CMSIS 包装多一层名字映射，调试看调用栈更绕。

- **中断优先级约束**：调用 FreeRTOS API 的中断（这里是 WiFi USART 与它的 DMA）抢占优先级数值必须 ≥ 5；数值小于 5 的中断不得调用 `FromISR` API。
- **HAL 时基必须从 SysTick 改到 TIM6**。
- 互斥量：`state_mutex`、`dbg_uart_mutex`。
- **堆监控责任人：ControlTask**。10ms 轮询里每 3000 次（30 s）打印一行 `xPortGetFreeHeapSize` / `xPortGetMinimumEverFreeHeapSize`。

| 报警类型 | 频率 | 节奏 |

> 这个功能只存两个参数（阈值、时长），修硬件与删功能之间选了后者：整套 I2C1 + 24C02 + ConfigTask 已删除，
> 参数改为只在内存生效。第 1 条那条"待实物确认"随之作废。

**待实物确认项**（板子到手后各花一分钟，用万用表通断档）：

1. PF8 与蜂鸣器基极电阻 R37 是否连通；
2. LED0/LED1 是否共阳（低电平点亮）——原理图给了结论，实物复核一遍更稳。

## 四、业务逻辑

### 状态机（MUTED 闭环）

```text
WAITING ──按键开机──► COUNTDOWN ──报警条件成立──► ALARM
   ▲                      ▲                          │
   └──── 复位/stop ───────┴─── 报警条件全部解除 ─────┘

静音标志 muted：只在 ALARM 期间可置位；报警解除或复位时自动清零
```

| 迁移 | 触发条件 |
|---|---|
| WAITING → COUNTDOWN | 按开关机键，`switch_on=1`，`remain_s = duration_s` |
| COUNTDOWN → ALARM | `temp_alarm`（温度 ≥ 阈值）或 `countdown_alarm`（`remain_s == 0`）成立 |
| ALARM → COUNTDOWN | 两个报警条件**同时**解除：温度降回阈值以下，**且** `remain_s > 0` |
| ALARM → WAITING | 按复位键，或 MQTT 下发 `reset` / `stop` |
| COUNTDOWN → WAITING | 按复位键，或 MQTT 下发 `stop` / `reset` |
| `muted` 置位 | ALARM 期间按静音键 |
| `muted` 清零 | 报警条件全部解除时自动清零；复位时清零 |

**倒计时归零是保持型报警**——`remain_s == 0` 一直成立，静音后仍是 ALARM，必须复位才回 WAITING。**温度报警是可自愈型**——温度降回阈值以下且倒计时未归零，自动回 COUNTDOWN。

### 关键实现约定

- **按键**：30ms 时间窗 + 状态机消抖，ControlTask 每 10ms 轮询一次，全程不用 `delay()`；改参数是内存操作，不会占用按键响应。
- **倒计时**：tick 计数（毫秒累加），不在任务里阻塞等待。
- **报警输出**：PF8 走 **TIM13_CH1** PWM——温度报警 2 kHz、倒计时报警 3 kHz，节奏均为响 200ms / 停 150ms；静音时停 PWM，`state` 保持 ALARM。
  TIM13 挂在 **APB1**（已按 CMSIS 头文件复核：`TIM13_BASE = APB1PERIPH_BASE + 0x1C00`），
  在 42 MHz 的 APB1 上（预分频≠1）定时器时钟是 84 MHz，所以 **PSC 取 83** 得到 1 MHz 计数（v10 按 TIM11 在 APB2/168 MHz 写的 167 作废）；
  ARR/CCR 不变：2 kHz → ARR 499 / CCR 250，3 kHz → ARR 332 / CCR 166。
- **DHT11**：40 bit 单总线时序 + 校验和验证，位级延时用 DWT CYCCNT 或专用 TIM，**禁止 `HAL_Delay`**。读取失败不重试当前周期，记日志等下个 2s 周期重读。
- **配置不持久化（v12）**：阈值与时长只在内存生效，断电回默认值（40 ℃ / 60 s）。原来那套 24C02 + CRC8 +
  8 字节页拆包已整体删除，根因是板载 24C02 的 SCL 断线（见第三节 v12 追记）。

## 五、WiFi 与 MQTT

### 配置宏清单（换 broker 时必须整组改）

| 宏 | 当前值（占位，用前必换） | 换成公共 broker 时 |
|---|---|---|
| `MQTT_BROKER` | `"easyiothings.com"` | `"broker.emqx.io"` |
| `MQTT_PORT` | 1883 | 1883 |
| `DEVICE_ID` | `0u`（占位） | 自定义唯一编号 |
| `MQTT_TOPIC_UP` | `"Data/replace_with_your_device_id"`（占位） | 如 `"moxa/200001/up"` |
| `MQTT_TOPIC_DOWN` | `"Sub/replace_with_your_device_id"`（占位） | 如 `"moxa/200001/down"` |
| `MQTT_CLIENT_ID` | `"replace_with_your_client_id"`（占位） | 需全局唯一 |
| `MQTT_LWT_PAYLOAD` | `{"type":"status","online":false}` | 同 |
| `WIFI_SSID` / `WIFI_PASSWORD` | 占位串（`replace_with_your_ssid` / `..._password`） | 换网时重编译 |

### 模组与实现分支

模组接在 **USART3**（PB10=TX / PB11=RX），使能脚 CH_PD（PF6）拉高后模组才工作。**M4 第一件事是 AT 能力探测**：支持 MQTT AT 指令（乐鑫官方 AT ≥ v1.2）→ 用 `AT+MQTTCONN` / `AT+MQTTPUB` / `AT+MQTTSUB` 推进；不支持 → 换一块已刷 AT ≥ v1.2 的 ESP-01S。不保留"透传 + 手写 MQTT 报文"分支。

### NetTask 的 AT 命令状态机

**收发方式**：USART 用 **IDLE 中断 + DMA 接收**到环形缓冲，发送用 DMA。**禁止使用阻塞式 `HAL_UART_Receive(..., 2000)`**。

**并发粒度：同一时刻只允许一条在途 AT 命令。** 不做命令交错、不做响应归属匹配，状态机保持线性。代价是排在后面的命令最多等待一个命令周期（≤2 s）。

NetTask 主循环每轮做四件事：

1. 若当前无在途命令，从 `at_tx_queue` 取一条发送。
2. 用 0 超时收 `ack_queue`，取到的 ACK 放进 `at_tx_queue`（`state` 字段原样搬过去，不刷新）。
3. 每 3 s 向 `at_tx_queue` 放一条 `AT_TX_TELEMETRY`（不预先组装 JSON）。
4. 等待响应期间分片推进：每 200 ms 推进一次心跳，同时解析 URC、扫描环形缓冲。

**组装遥测必须先取快照**：`g_moxa_state` 由 `state_mutex` 保护，NetTask 组装 JSON 前要加 `state_mutex` 把状态拷到自己的**静态快照结构**，**释放锁之后**再拼 JSON。否则可能读到 ControlTask 写到一半的状态（比如 `state` 已更新但 `remain_s` 还是旧值），上报出自相矛盾的组合。

每条 AT 命令 2 s deadline，超时按命令类型决定重试或计错。**等待响应期间必须同时解析 URC**（`+MQTTDISCONNECTED`、`+MQTTSUBRECV`、`WIFI DISCONNECT` 等）。

**MQTT 保活归属**：AT+MQTT 模式下 keepalive 由模组负责，**F407 侧不发 PINGREQ**；设备侧只监听 URC 判断离线并重连。

### 连接流程与失败处理

上电 → AT 测试 → 设 WiFi 模式 → 连 AP → 建 TCP → MQTT CONNECT（带 LWT）→ 订阅下行主题 → 周期发遥测。任一环节断开进入重连状态机，每 2s 重试。参数沿用旧 `config.h`：keepalive 60s、socket 超时 2s、遥测周期 3000ms。发布失败不落盘，只累加 `err_cnt`，等下一个 3s 周期重发。

### 报文规范

**遥测**（`type: "telemetry"`）：

```json
{"type":"telemetry","device_id":1,"temp_c":28,"humi_pct":55,"remain_s":42,
 "state":"COUNTDOWN","temp_alarm":0,"countdown_alarm":0,"muted":0,"th_max_c":45,
 "duration_s":1800,"err_cnt":0,"uptime_s":86400,"fw":"f407-v1"}
```

**无 `ts` 字段**：设备没有 RTC 也没有授时通道，时间基准由 MQTT 客户端或平台的接收时刻决定。

**指令**（下行）：`{"msg_id":17,"cmd":"set_threshold","value":45}`，支持 `start`、`stop`、`reset`、`mute`、`query`、`set_threshold`、`set_duration`。

**回执**（`type: "ack"`）：`{"type":"ack","msg_id":17,"cmd":"set_threshold","result":"ok","code":0,"state":"COUNTDOWN"}`

`code`：0 成功 / 1 未知指令 / 2 参数非法 / 3 忙 / 4 格式错误 / 5 配置读写失败（v12 起保留编号但不再产生——没有持久化了）。

**状态**（`type: "status"`）：`{"type":"status","online":true}`，retained；LWT 发 `{"type":"status","online":false}`。

### 数据查看

不做 PC 端程序。用现成 MQTT 客户端（MQTTX 或平台网页控制台）订阅查看与下发。

## 六、健壮性设计

### 心跳预算与看门狗时间推导

| 任务 | 心跳推进位置 | 最长允许间隔 |
|---|---|---:|
| ControlTask | 每轮 10ms 轮询末尾 | 100 ms |
| AlarmTask | 每 50ms 一次 | 500 ms |
| SensorTask | 采集开始前 + 结束后各一次（覆盖 4ms 阻塞） | **2.5 s** |
| NetTask | AT 等待循环内每 200ms 推进一次 | 2 s |

- **DogTask 周期 500ms**，比对各任务 `last_checkin_tick` 与上表期限，任一超限即停止喂狗。
- **IWDG 超时 4s**（LSI ≈32kHz，预分频 32 → 1ms/tick，重装值 4000）。
- 心跳由任务自身推进，不由 DogTask 代填。

**最坏复位时间推导**：

```text
最坏复位时间 = 最大心跳期限 + DogTask 检查周期 + IWDG 超时
             = 2.5 s + 0.5 s + 4 s
             = 7.0 s
```

验收标准按 **≤8 s** 执行。每次改动心跳期限或 IWDG 超时，都要重算这个式子并同步更新验收值。

SensorTask 期限取 2.5 s，是因为它每 2 s 一个采集周期、在采集前后各推进一次心跳，实际间隔约 2 s。（v12 删掉 ConfigTask 后这条 2 s 期限自然消失，最坏复位时间不受影响——最大期限仍是 SensorTask 的 2.5 s。）

### 其他

- **DEBUG 期必须冻结 IWDG**：置位 `DBGMCU_APB1_FZ` 的 `DBG_IWDG_STOP`，或 Debug 构建不启动 IWDG。
- **复位来源识别**：开机读 RCC 复位标志，若为看门狗复位则串口明确打印。
- **错误计数**：AT 失败、MQTT 连接失败、JSON 解析失败、队列满丢弃、非法指令、缺失 msg_id 分别计数，汇总进 `err_cnt`（只在内存）。（v12 删掉"配置 IO 失败"与"token 不匹配"两类。）

## 七、里程碑

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| **M0 硬件闸门**（已完成） | 确认 DHT11 引脚、WiFi 串口、蜂鸣器有源/无源 | 已完成：DHT11=PG9、WiFi=USART3（PB10/PB11）+ 使能 PF6、蜂鸣器=无源接 PF8 |
| M1 工程骨架 | CubeMX 配时钟树、USART/I2C/GPIO/TIM6，Keil 工程 + 原生 FreeRTOS API 空跑 | 串口能打印；6 个任务按心跳表推进；无栈溢出告警；ControlTask 每 30s 打印堆占用；运行 10 分钟后 `xPortGetMinimumEverFreeHeapSize ≥ 8 KB` |
| M2 单外设打通 | DHT11（PG9）、按键、蜂鸣器 PWM（PF8） | 每个外设单独跑通并有串口证据 |
| M3 业务闭环 | 状态机（含静音闭环）、倒计时、报警、复位、改参数（内存生效）、ACK 生成 | 按键 + LED + 串口跑通全流程；`set_threshold` 生效并回 ACK（v12 起不落盘）；改参数期间连续按静音键响应 ≤50ms |
| M4 联网与 MQTT | AT 能力探测；单在途 AT 命令状态机；WiFi 连接、MQTT 上线、遥测、指令、ACK 回传、遗嘱、重连 | 见下方 M4 专项出口条件 |
| M5 健壮性 | IWDG、按心跳表实现 DogTask、复位标志识别 | 满足第八节全部验收标准 |

### M4 专项出口条件（量化）

1. MQTT 客户端能看到遥测；7 种指令收到正确 `code` 的 ACK。
2. 拔网后自动重连并恢复上报。
3. **AT 等待量化**：连续运行 1 小时，其中**至少包含 3 次 AT 等待接近 2s deadline 的场景**（可人为把 deadline 压到 2s 触发），**全程无看门狗复位**。
4. **DHT11 联网复测**（500 个周期，记录总失败率与最大连续失败次数）：
   - 总失败率 ≤1% 且最大连续失败 ≤2 → 直接通过。
   - 最大连续失败 3~4 次 → **记录实测值，把验收标准放宽到"实测值 +1 次余量"并注明原因**，通过。理由是引入输入捕获会偏离本项目重点，收益不抵工作量。
   - 最大连续失败 ≥5 次 → **引入 TIM 输入捕获方案**替换 GPIO 轮询，改完重新测。
     这条阈值定在 5 次，因为连续失败 5 次意味着约 10 秒无有效温度数据，已经会影响控温功能的观感。

## 八、验收标准

- **DHT11**：连续 500 个采集周期，总失败率 ≤1%、最大连续失败 ≤2；M4 联网后按上节规则复测。
- **ACK 闭环**：7 种指令逐条下发，各收到正确 `code` 的 ACK；越界值返回 `code=2`；`cmd_queue` 塞满时由 NetTask 回 `code=3`；缺失 `msg_id` 返回 `code=4`。（v12：`code=5` 与"配置在途 `code=3`"随持久化一起删除。）
- **判定顺序**：`cmd` 未知且 `value` 越界的指令，返回 `code=1`（先判 cmd）。
- **ControlTask 不被阻塞**：改阈值/时长期间连续按静音键，响应延迟 ≤50ms（内存操作，天然不阻塞）。
- **状态机一致性**：`state`、LED 表现、蜂鸣器节奏三者一致；倒计时归零后静音，`state` 仍为 ALARM 且 `muted=1`，复位后回 WAITING 且 `muted=0`。
- **看门狗有效性**：人为制造死循环，**≤8s** 内触发复位（推导值 7.0s），串口重启日志由 RCC 标志识别。
- **看门狗不误报**：按 M4 专项出口条件第 3 条执行。
- **端到端延迟**：**正常在线状态（无重连）** 下，温度变化到 MQTT 客户端可见 ≤5s。
- **堆稳定**：连续运行 1 小时，`xPortGetFreeHeapSize` 不出现单调下降。
- **配置不持久化（v12）**：修改阈值与时长后断电重启，参数回到默认值（40 ℃ / 60 s）——这是明确取舍，不是缺陷。
- **网络重连**：关闭 AP 后进入重连，恢复后自动上线并继续上报（不含历史数据补发）。

## 九、踩坑点清单

1. **HAL 时基必须改到 TIM6**。
2. **调用 FreeRTOS API 的中断优先级数值必须 ≥5**。
3. **IWDG 一旦启动无法关闭**，调试期必须用 `DBG_IWDG_STOP` 冻结。
4. **板级连接要实测，别只信原理图**：v12 就是实测发现 24C02 的 SCL（6 脚）与 PB8 不通（该脚 0 V，而 SDA 正常、与 PB9 导通）才删掉配置持久化的。原理图只保证"设计上连着"，虚焊/断线它画不出来——这一条也是"芯片级事实靠芯片库、板级事实靠实物"那条原则的实例。
5. **DHT11 位级延时不能用 `HAL_Delay`**，用 DWT 或专用 TIM。
6. **事件组每个消费者一个专属位**，共用位 + clear-on-exit 会让广播退化成点对点。
7. **心跳按任务设期限，长等待内部必须推进心跳**；改期限后必须重算最坏复位时间并同步验收值。
8. **ACK 路径只有一条**：ControlTask 生成 → ack_queue → NetTask 发布；唯一例外是 cmd_queue 入队失败的 busy 兜底。ACK 的 `state` 取生成时刻，不在发送时刷新。
9. **NetTask 禁止阻塞式 AT 收发**；**同一时刻只允许一条在途 AT 命令**。
10. **组装遥测前先取 `state_mutex` 快照**，释放锁后再拼 JSON。
11. **改参数是同步内存操作**（v12 起）：`set_threshold` / `set_duration` 直接生效并回 `code=0`，没有异步回执、没有 token 匹配；`code=5` 与"配置在途 `code=3`"两条错误路径已删除，协议里只保留编号。
12. **ControlTask 不做阻塞等待**：改参数不占用按键响应；开机路径上也不再需要"调度器之前读 I2C"这类硬约束。
13. **`uptime_s` 用独立秒计数器**，不要 `HAL_GetTick()/1000`（49.7 天回绕）。
14. **NetTask 的 JSON / AT 缓冲必须静态分配**；队列只传固定结构体。
15. **换 broker 要整组改宏**（地址、端口、device_id、上下行主题、client id、LWT）。
16. **AT 不支持 MQTT 就换模组**，不手写 MQTT 报文。
17. **PF8 只能用 TIM13_CH1**（TIM11_CH1 在 PF7）。已按 CubeMX 芯片库复核：PF8 的定时器复用只有 TIM13_CH1 一个，v10 那种写法在 CubeMX 里根本选不出来。TIM13 在 APB1 → 定时器时钟 84 MHz，PSC 取 **83**（不是 TIM11 在 APB2 时的 167）。
18. **查"某只脚能不能走某个外设"用 CubeMX 自带的芯片库，别信二手网络名表**：CubeMX 安装目录下的芯片库（`db\mcu\STM32F407Z(E-G)Tx.xml`）是 ST 官方数据，一行命令就能查出某脚的全部复用。但要分清两类事实——**芯片级**（这只脚在芯片上有没有这个复用）用芯片库就能定死；**板级**（这只脚在板上接到了谁）必须看原理图或实物通断。v10 那两轮引脚错误的根因，都是把板级事实当成了可以靠资料表推断的东西。
19. **KEY 区没有外部上拉/下拉电阻**，三个按键的平时电平靠 **MCU 内部上/下拉**：PA0 配 Pull-down、PE3/PE4 配 Pull-up。配成 `No pull` 会浮空，表现为幽灵按键或按键失灵，而且随环境漂移、很难查。
